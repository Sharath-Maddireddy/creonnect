# Trend Recommendations Handover

## Purpose

Trend Recommendations turns a creator's account analysis and current trend signals into actionable content ideas. A user can generate recommendation cards, save an idea, create format-appropriate execution assets, organize ideas, and schedule them.

This guide is for the engineering and product owners responsible for operating and extending the feature.

## User Flow

1. The user opens the Content Suggestions page at `/trends` and searches for a creator account.
2. The frontend requests the creator's trend recommendation data and renders the opportunity summary, recommended content angles, insights, niche, trends, content gaps, and available audio metadata.
3. The user selects **Generate Full Ideas**. The API creates an idea-generation job and returns a job ID.
4. `worker-content` processes the job, stores generated ideas, and updates job progress.
5. The frontend polls the job-status endpoint until it is completed or failed, then reloads ideas.
6. The user can save an idea and generate the downstream asset appropriate to its format.
7. The user can improve, regenerate, duplicate, vary, group, or schedule saved ideas.

## Architecture

### Frontend

- Main page: `frontend/src/pages/TrendRecommendations.jsx`
- Route: `/trends`
- Responsibilities: creator search, rendering recommendation cards and sidebar data, starting jobs, polling status, and launching script/caption/slide flows.

### API

- Primary router: `backend/app/api/content_suggestion_routes.py`
- Router is registered by `backend/main.py`.
- Account access is restricted to the signed-in Instagram account through `require_current_account`.
- Router prefix: `/api/v1/accounts`.

Key endpoints, relative to `/api/v1/accounts`:

| Endpoint | Responsibility |
| --- | --- |
| `POST /{account_id}/trends/generate-ideas` | Queue full-idea generation. |
| `GET /{account_id}/trends/generate-ideas/{job_id}/status` | Read full-idea job progress. |
| `GET /{account_id}/ideas/jobs/{job_id}/status` | Read improve, variation, or regenerate job progress. |
| `GET /{account_id}/trends/ideas` | List persisted generated and saved ideas. |
| `POST /{account_id}/trends/persist-idea` | Persist a recommendation before a downstream action. |
| `POST /{account_id}/trends/generate-script` | Generate a reel/video script. |
| `POST /{account_id}/trends/generate-caption` | Generate a caption. |
| `POST /{account_id}/ideas/{idea_id}/improve` | Queue idea improvement. |
| `POST /{account_id}/ideas/{idea_id}/variations` | Queue idea variations. |
| `POST /{account_id}/ideas/{idea_id}/regenerate` | Queue regeneration. |
| `POST /{account_id}/ideas/{idea_id}/generate-thumbnails` | Generate thumbnails. |
| `POST /{account_id}/planner/schedule` | Schedule an idea. |
| `GET /{account_id}/planner/calendar` | Fetch calendar data. |
| `POST /{account_id}/trends/ai-assistant` | Run the Prompt Assistant. |

### Jobs and Persistence

- Job orchestration: `backend/app/services/content_suggestion_jobs.py`
- Recommendations are generated by the trend recommendation engine in `backend/app/analytics/trend_recommendation_engine.py`.
- Jobs and idea state are stored in the database. The key job model is `IdeaGenerationJob`; ideas are stored as `Idea` records.
- A queue-enqueue failure is persisted as a failed job with a user-safe message. The API must not perform the LLM work synchronously as a fallback.

### Workers

RQ and Redis are required for asynchronous generation.

| Process | Queues |
| --- | --- |
| `worker` | `account-analysis`, `single-post-analysis`, `embedding-ingestion` |
| `worker-content` | `trend-analysis`, `content-suggestions` |

`worker-content` is mandatory for Trend Recommendations. Starting only the standard worker causes idea generation to remain queued or appear stuck.

## Operations

### Production

`docker-compose.prod.yml` defines the required services:

1. `migrate` runs `alembic upgrade head` once.
2. `redis` provides job queue storage.
3. `api` serves the backend.
4. `worker` processes account-analysis jobs.
5. `worker-content` processes trend and content-suggestion jobs.

The API and both workers depend on migrations completing successfully. Redis is password-protected through `REDIS_PASSWORD`.

### Local Development

Run the API, Redis, and both worker roles. If workers are not being orchestrated by Docker, use the RQ worker module with the queue list set explicitly:

```powershell
$env:RQ_QUEUES = 'account-analysis,single-post-analysis,embedding-ingestion'
python -m backend.app.workers.rq_worker
```

In a second terminal:

```powershell
$env:RQ_QUEUES = 'trend-analysis,content-suggestions'
python -m backend.app.workers.rq_worker
```

Run database migrations before testing a new environment:

```powershell
alembic upgrade head
```

## Required Configuration

Configure values in the deployment secret store or `.env`; never commit them.

| Variable | Why it is required |
| --- | --- |
| `DATABASE_URL` | Persists ideas, jobs, account analysis, and schedules. |
| `REDIS_URL` or `REDIS_PASSWORD` | Connects API and workers to the RQ backend. |
| LLM provider credentials | Produces recommendations and downstream assets. Use the provider configured by `LLMClient`. |
| Instagram OAuth/session configuration | Authenticates the account and enforces account ownership. |

## Format-Specific Execution

The downstream action must match the idea's format:

- Reel/video ideas: generate a script and caption.
- Carousel ideas: generate slides and a caption.
- Photo ideas: generate a photo-post brief and caption; do not present a reel script as the primary asset.

When changing supported formats, update the frontend action labels and the backend generation contract together.

## Monitoring and Troubleshooting

### Ideas remain on "Generating"

1. Confirm Redis is running and reachable from the API and workers.
2. Confirm `worker-content` is running.
3. Confirm its `RQ_QUEUES` includes `trend-analysis,content-suggestions`.
4. Inspect the matching `IdeaGenerationJob` row and its `status`, `step_label`, `percent_complete`, and `error_message`.
5. Inspect `worker-content` logs for the job ID and LLM/provider errors.

### "Idea not found in the database yet"

The user attempted a downstream action before the recommendation was persisted. Generate full ideas first, save the recommendation, or use the persist endpoint before requesting a script, caption, or slides.

### Job fails immediately

- Check queue connectivity and Redis credentials.
- Check that the database schema is current.
- Check LLM credentials, provider availability, and rate limits.
- Confirm the requested account has completed analysis data and the authenticated account matches the URL account ID.

### No useful recommendations or sidebar data

- Verify the creator has a recent account analysis and trend-analysis result.
- Inspect source trend data and the creator niche/context used by the recommendation engine.
- Do not substitute invented audio titles or trend metrics when provider data is unavailable. Show data availability clearly instead.

## Security and Data Rules

- All account-scoped endpoints must verify the authenticated Instagram account owns the requested `account_id`.
- Treat generated ideas and schedules as account-scoped data; query by both resource ID and account ID.
- Keep API keys and database credentials out of source control, diagnostics, frontend bundles, and logs.
- Do not expose a static server API key to the browser. Use the signed-in session for first-party UI requests.

## Known Limitations

- The availability and specificity of recommendations depend on completed account analysis, trend data, and the configured LLM provider.
- Trending-audio output is only as reliable as its source data. It must not claim a guaranteed Instagram track title without a verified provider source.
- Content-type-specific generation is still evolving. Verify carousel and photo actions remain distinct from reel-script generation after any UI or prompt change.
- Prompt Assistant is a separate interaction surface and should be tested with the same account-ownership and queue/LLM failure handling as idea generation.

## Ownership Checklist

- Product owner: owns user-facing behavior, copy, and acceptance criteria.
- Backend owner: owns API contracts, database migrations, LLM integrations, and authorization.
- Platform owner: owns Redis, both RQ workers, environment configuration, deployment, and alerts.
- Frontend owner: owns polling behavior, error states, format-specific actions, and accessibility.
- Support owner: uses the troubleshooting checklist and records job ID, account ID, timestamp, and worker logs for incidents.

## Walkthrough Preparation

Use this sequence in the live handover:

1. Show the `/trends` page and explain the recommendation cards and sidebar data.
2. Generate full ideas and show job progress moving from queued to completed.
3. Demonstrate reel, carousel, and photo downstream actions.
4. Save an idea, add it to a collection, and schedule it.
5. Stop `worker-content` in a non-production environment to show the expected failure mode and recovery steps.
6. Show the API route, database job record, Redis queue, and worker logs for the same request.
